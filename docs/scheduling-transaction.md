# Reversible serial-render diagnostic

`tools/run_benchmark.py --serial-render` opts into a temporary scheduling change for the bounded diagnostic. Without the flag, the runner leaves scheduling restrictions untouched and preserves the user's parallel-render preference in its unique diagnostic hardware input. This scheduling flag alone does not enable VR.

The supported `system/hardware_settings_restrictions.xml` has six CPU branches that override `parallelUpdateRender` to `true`, including the hyper-threading branch, followed by a `false` fallback. This explains why requesting `false` in a hardware input alone is insufficient. The original file is pinned to SHA-256 `45257db5fa64d833575d569ec6f3b03344b5f40be25830960a8d11783276470b`.

Preflight reads that file, verifies its exact hash and CPU branch signature, and prepares a byte-preserving change of only those six `true` values to `false`. Worker maps, processor affinities, the existing fallback, other settings, comments and formatting stay unchanged. An unrecognized or read-only restriction file is rejected. Preflight without `--run` does not create a journal, backup or installed file.

For an authorized run, the transaction writes and verifies `restrictions-original-<run-id>.bin` beside `deployment.json`, then durably records its original/applied hashes and fixed target name in a schema-3 journal **before** replacing the installed restriction file. The target is hash-checked again immediately before the atomic replacement. The user hardware settings file is not replaced: the runner still creates `dirt3vr-hardware-<run-id>.xml` in the game's actual Documents hardware-settings directory and references that unique filename from the benchmark configuration.

Recovery validates the complete journal, backup hash, derived applied-state signature and all temporary-file hashes before making changes. It restores the restriction file only from the exact expected applied state; an already-original file is accepted after an interrupted preparation or restoration. Missing targets, changed backups, foreign edits or invalid journal paths are preserved for review. Any conflict prevents the initial recovery pass from deleting temporary files. The backup and receipt remain available after successful restoration. Existing schema-1 and schema-2 temporary-file journals remain recoverable.

Use the runner's existing `--recover <deployment.json>` after closing DiRT 3 if an interrupted run leaves a pending deployment. The runner resolves the actual Documents directory again and rejects a mismatched recorded hardware-settings location. Do not delete or replace a conflicting original manually without comparing the retained backup and current file.

A serial diagnostic is complete only when the game produces the requested Aspen/route_0/Fiesta benchmark result with nonzero samples, D3D11 and the requested graphics settings, and that result records `cpu/threadStrategy/@parallelUpdateRender="false"`. Proxy loading or Present calls alone are insufficient. Completion also requires a normal process exit, no forced termination, successful restoration and unchanged protected files. `run.json` records the requested scheduling mode, original/applied restriction hashes, observed configuration and `serialRenderVerified`.

Fixture tests cover the minimal semantic transform, opt-in behavior, pre-write journaling, interrupted recovery, damaged backups, concurrent edits, foreign proxies, malformed paths and a game result that re-enables parallel scheduling. Live scheduling and render-order acceptance must be established by a separately authorized bounded run.

The separate `--replay-pair` diagnostic requires both `--serial-render` and `--scene-observer`; invalid combinations fail before filesystem access. Only this explicit flag puts `DIRT3VR_REPLAY_DIAGNOSTICS=1` in the child environment. Baseline diagnostics clear inherited replay and VR activation flags. The replay mode remains a desktop experiment with `mode="desktop-eye-replay"`, `stereo=false` and `stereoVerified=false`; it opens no OpenXR session.

Replay acceptance additionally requires exactly 120 consecutive positive main-scene sequence numbers, each ready and restored with exactly two render calls on the same frame. The native window starts 45 seconds after its first main scene, so its starting sequence depends on rendering speed. The recorded history counter must advance once and remain equal between eyes, and Present must not advance between eye calls. Only pair offsets 0, 60 and 119 are sampled, with positive vertex, primitive and pixel statistics for both eyes. Every native `Replay refused` or `Replay failed` message prevents completion.

The six required captures are `replay-<actual-main-sequence>-eye0.bmp` and `replay-<actual-main-sequence>-eye1.bmp` for those three sampled pairs, in the run's log directory. The runner checks the native 1280×720 top-down 32-bit BMP headers and complete file lengths and records each capture's hash. Missing, extra or malformed captures prevent completion. These checks establish bounded replay evidence only; they do not establish correct binocular geometry, headset output or visual acceptance. The full evidence and rejection reasons appear under `run.json`'s `replaySummary`.

## Explicit headset prototype

`--xr-runtime "C:\absolute\runtime-32.json" --serial-render --scene-observer --seconds 180` opts into the native headset prototype. It requires a duration from 120 through 300 seconds and cannot be combined with `--replay-pair`. Without `--run`, the command still performs only read-only preflight. The manifest must be an absolute existing JSON file, its declared library must be an existing x86 PE32 Windows DLL, and both hashes are recorded. No registry entry is changed. Runtime availability, headset tracking and successful session creation remain live checks performed by the native prototype.

Only the owned child receives `DIRT3VR_XR_PROTOTYPE=1`, the explicit `XR_RUNTIME_JSON`, and `DIRT3VR_XR_STOP_FILE=<run-directory>/xr-stop.request`. Baseline environments clear inherited prototype, runtime-override and stop-path variables. The report uses `mode="headset-prototype"`, `stereo=false` and `stereoVerified=false`; prototype evidence is not a claim that VR driving is ready.

Because the benchmark can exit by itself, the runner creates the stop-request file at 90 seconds of wall time while the desktop benchmark continues. It waits up to three seconds for `XR prototype shutdown complete`, and checks again before any explicit WM_CLOSE if necessary. This asks the native render thread to release its session and graphics objects before the process exits. Missing acknowledgement, an unexpected native stop, forced termination or an early natural exit prevents diagnostic completion.

`xrSummary` requires valid sparse submission records with strictly increasing main sequence and submitted-frame totals, at least 120 total submitted frames, restored cameras and positive projection uploads for both eyes. The two history counters must agree and match the logged `history_expected_advance` (0 or 1), including unsigned-32-bit wrap. Only `XR prototype stopped reason=runner-stop-file` is an expected stop; failed/refused messages, malformed records and missing shutdown completion are failures. All existing benchmark, restoration and protected-file requirements still apply. User-confirmed headset appearance, camera choice and comfort remain separate acceptance steps.
